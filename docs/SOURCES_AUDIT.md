| Karger §4.2 (`consistent-hashing`, data2.ts:181) | Hash servers and keys onto one circle; each key belongs to the next server clockwise; a new server takes only its arc | Matches with a qualifier: Karger maps buckets and items to the unit interval and assigns each item to the *closest* bucket point. “Next clockwise” is the Dynamo/Chord convention (Dynamo is also cited for this topic). | Karger §4.2 (`consistent-hashing`, data2.ts:182) | Several points per server (virtual nodes) even out the arcs | Matches: each bucket is replicated κ·log C times on the interval so that, with high probability, each bucket owns O(1/\|V\|) of it (balance). | Sagas §1, §9 (`distributed-transactions`, distributed3.ts:227) | Sagas aren't isolated: others see in-between state; some actions can't be undone | Matches: “other transactions might see the effects of a partial saga execution”; firing a missile may not be undoable. “Do irreversible steps last” is the lesson's design advice, not stated in the paper. 2PC and the outbox are not in this paper. |
| LSM-tree §2 (`storage-engines`, data1.ts:179–180) | Log first, then an in-memory sorted table; the log recovers it after a crash | Matches: a log record is first written to the sequential log, then the entry is inserted into the memory-resident C0 tree; the logical log recreates lost C0 contents on recovery. |
