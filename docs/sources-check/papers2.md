# Sources check: papers2 batch (2026-11-20)

PDFs read with curl + pdftotext: Karger (cs.princeton.edu), Lamport (lamport.azurewebsites.net), Gilbert & Lynch 2002
(groups.csail.mit.edu, `Brewer6.pdf`), Sagas (cs.cornell.edu), LSM-tree (cs.umb.edu), Berenson et al. (arxiv.org, the
Microsoft Research tech report MSR-TR-95-51 version of the SIGMOD 1995 paper), MIT 6.5840 Spring 2026 notes and Lab 3A
(pdos.csail.mit.edu).

Note on Gilbert & Lynch: the URL first given (`groups.csail.mit.edu/tds/papers/Gilbert/Brewer2.pdf`) is the 2012 IEEE
Computer paper “Perspectives on the CAP Theorem”, not the 2002 paper our entry cites. The 2002 SIGACT News paper was read
from `Brewer6.pdf` on the same host, and the entry's URL points there.

| Source (section) | Lesson claim | Result |
|---|---|---|
| Karger §4 intro, §4.1, §4.2, Thm 4.1 (`consistent-hashing`, data2.ts:180) | Modulo hashing moves most keys when N changes | Matches: the paper says that with a classical hash such as `ax + b mod p`, changing the range moves almost every item and makes cached data useless. |
| Karger §4.2 (`consistent-hashing`, data2.ts:181) | Hash servers and keys onto one circle; each key belongs to the next server clockwise; a new server takes only its arc | Matches with a qualifier: Karger maps buckets and items to the unit interval and assigns each item to the *closest* bucket point. “Next clockwise” is the Dynamo/Chord convention (Dynamo is also cited for this topic). Monotonicity (Thm 4.1 proof): when a bucket is added, only items now closest to it move, none move between old buckets. No wording change; the difference is recorded in the entry's note. |
| Karger §4.2 (`consistent-hashing`, data2.ts:182) | Several points per server (virtual nodes) even out the arcs | Matches: each bucket is replicated κ·log C times on the interval so that, with high probability, each bucket owns O(1/\|V\|) of it (balance). The term “virtual nodes” and the count of 50 are the lesson's own. |
| Karger (`consistent-hashing`, data2.ts:182 predict) | Removing a server moves only the keys it owned | Matches by monotonicity (defined for growing views; the reverse follows from the same property). |
| Karger (`consistent-hashing`, data2.ts:190) | Dynamo-style databases and many cache clients use consistent hashing | Partly covered: the paper's setting is web caches with clients holding different “views”. Use in Dynamo-style databases is covered by the Dynamo entry, not by Karger. |
| Lamport, Logical Clocks: IR1, IR2 (`clocks-ordering`, distributed2.ts:187 and python/sdm/clocks.py) | Counter per server, +1 per event, attach to messages, receiver jumps ahead of sender's counter; if X could have caused Y, X's number is smaller | Matches (IR1, IR2(a)/(b), Clock Condition: a → b implies C(a) < C(b); → means a could causally affect b). `receive = max(self.time, sent_at) + 1` satisfies IR2(b). |
| Lamport, Clock Condition and Ordering the Events Totally (`clocks-ordering`, distributed2.ts:190 predict) | Lamport numbers don't prove an order between unrelated events; the numbers break the tie | Matches with a qualifier: the converse of the Clock Condition does not hold; concurrent events have no happened-before order and the total order uses an arbitrary tie-break. **Fixed wording**: “Unrelated events have no real order” → “no causal order”. The vector-clock remark is not from this paper. |
| Lamport, Physical Clocks PC1–PC2 (`clocks-ordering`, distributed2.ts:185) | Clocks drift; synchronisation keeps them close but never identical | Matches in principle (drift rate κ, synchronisation bound ε). NTP, “typically within milliseconds” and backward jumps are not from this paper. |
| Gilbert & Lynch 2002 §2.1–2.3 (`cap-quorums`, distributed2.ts:254) | During a partition a system can't be both consistent (linearizable: every read sees the latest write) and available (every replica answers) | Matches with a qualifier: consistency is atomic/linearizable (total order, each operation looks instantaneous); availability means every request received by a non-failing node must get a response. **Fixed wording**: “(every replica answers)” → “(every working replica answers every request)”. “Every read sees the latest write” is a simplification of linearizability; kept. |
| Gilbert & Lynch 2002 §3.1 Thm 1 proof (`cap-quorums`, distributed2.ts:254) | Berlin either answers without checking (maybe wrong) or refuses until the link returns | Matches: the proof partitions nodes into G1, G2 with all messages lost; a read in G2 after a write in G1 must either return the old value or not respond. |
| Gilbert & Lynch 2002 §3.2.1 (`cap-quorums`, distributed2.ts:259) | The minority side refuses; quorums | Matches in principle: quorum-based systems keep atomicity and give up liveness under some failure patterns. R + W > N and its caveats are not in this paper (Dynamo entry). |
| Sagas §1 (`distributed-transactions`, distributed3.ts:221) | Each step is its own local transaction with a compensating action that semantically undoes it; on failure the completed steps are compensated in reverse order | Matches: Ti / Ci, Ci undoes Ti “from a semantic point of view” (not necessarily restoring the old state); guarantee T1…Tn or T1…Tj, Cj…C1. The paper's sagas run inside one database system (or a collection of airline databases); applying them across services is the lesson's extension. |
| Sagas §1, §9 (`distributed-transactions`, distributed3.ts:227) | Sagas aren't isolated: others see in-between state; some actions can't be undone | Matches: “other transactions might see the effects of a partial saga execution”; firing a missile may not be undoable. “Do irreversible steps last” is the lesson's design advice, not stated in the paper. 2PC and the outbox are not in this paper. |
| LSM-tree §2 (`storage-engines`, data1.ts:179–180) | Log first, then an in-memory sorted table; the log recovers it after a crash | Matches: a log record is first written to the sequential log, then the entry is inserted into the memory-resident C0 tree; the logical log recreates lost C0 contents on recovery. |
| LSM-tree §2, Finds in the LSM-tree Index (`storage-engines`, data1.ts:181–185) | Full memtable flushed as an immutable sorted run; reads check newest first | Matches with a qualifier: O'Neil's design moves entries from C0 into larger disk-resident tree components with a rolling merge (writing multi-page blocks to new disk positions), rather than flushing whole immutable runs; finds search C0 first, then C1…CK. The memtable/SSTable form is Bigtable's (checked in the papers batch). No wording change; noted in the entry. |
| LSM-tree §1–§2 (`storage-engines`, data1.ts:187, 190) | LSM makes writes cheap and pays in merge work and reads that may check several components | Matches: deferred, batched index changes with sequential multi-page I/O; finds needing an immediate answer stay relatively costly and may have to visit each component. Bloom filters and RocksDB/Cassandra examples are not from this paper. |
| Berenson et al. §2.2, §4.1 (`transactions`, data2.ts:20–23) | Two read-modify-writes, one overwrites the other: a lost update | Matches: P4 r1[x]…w2[x]…w1[x]…c1; the lesson's interleaving fits it with the partner as T1. |
| Berenson et al. §2.2, §4.2 (`transactions`, data2.ts:30 table) | Dirty read, non-repeatable read, write skew (two transactions read overlapping data, write different rows, break a rule), phantom | Matches (P1, P2, P3, A5B). The paper's write-skew example is joint bank balances that may go negative as long as the sum stays non-negative; the on-call rota example is the lesson's own. |
| Berenson et al. §4.2 Remarks 8–9 (`transactions`, data2.ts:31) | Isolation levels (read committed, repeatable read/snapshot, serializable) prevent progressively more anomalies | **Overstated.** Snapshot isolation is stronger than read committed but not comparable with repeatable read: SI allows write skew (A5B), locking RR allows phantoms (A3). **Fixed wording**: now “repeatable read or snapshot … Repeatable read and snapshot isolation are not the same level: snapshot isolation still allows write skew.” |
| MIT 6.5840 Lecture 6 (`consensus`, distributed3.ts:23–28) | One leader per term chosen by majority; one vote per term; randomised timeouts make simultaneous elections unlikely; heartbeats; a stale leader sees the newer term and steps down | Matches (“a term has at most one leader”; “each server can cast only one vote per term”; randomness breaks symmetry; “old leader will see new term in an AppendEntries reply and step down, or won't be able to get a majority”). ~100 ms heartbeats and 180/260 ms timeouts are illustrative; Lab 3A limits heartbeats to 10 per second and cites the Raft paper's 150–300 ms election timeouts. |
| MIT 6.5840 Lecture 7 (`consensus`, distributed3.ts:25, 31) | Votes only for a log at least as up to date; committed when a majority stores an entry of the current term; any future leader has every committed entry | Matches (election restriction; “a committed operation” defined as majority persisted, known committed when the leader sees a majority in its current term; majority intersection). |
| MIT 6.5840 Lecture 9 ZooKeeper (`consensus`, distributed3.ts:35 list) | Coordination services (etcd, ZooKeeper) hold leader/config/lock facts; leader election through such a service with an expiring lease | Matches in principle: coordinator election via an ephemeral znode, session terminated when keep-alives stop; etcd described as influenced by ZooKeeper. Consul, CockroachDB and TiKV are not mentioned in these notes. |
