# Batch: books (official author/publisher summaries only)

Read 2026-11-20. No book text was read. Only what the authors publish openly: refactoring.com (Fowler's online catalog of
refactorings and the site's definition of refactoring), martinfowler.com/eaaCatalog (PoEAA pattern summaries),
Evans's free *Domain-Driven Design Reference* (2015 PDF, CC BY 4.0, pattern summaries extracted from the 2004 book), and two
martinfowler.com bliki articles (CodeSmell, TestDouble) used only to check claims, not to mark a book entry.

| Source (section) | Lesson claim | Result |
|---|---|---|
| refactoring.com home (definition) | Refactoring is a sequence of small behaviour-preserving changes; run the tests after each (`refactoring-lesson`) | Matches (“a series of small behavior preserving transformations … the system is kept fully working after each refactoring”; “taking small steps, and using frequent testing to detect mistakes”). Characterisation tests and separate refactoring commits are not on this page: unchecked. |
| Refactoring catalog: Extract Function, Move Function, Introduce Parameter Object, Replace Conditional with Polymorphism | Smell table rows: Extract function; Move function to that object; Introduce parameter object; Replace conditional with polymorphism (`refactoring-lesson`, manifest summary) | Matches: all four exist under these 2nd-edition names (aliases Extract Method, Move Method); the Replace Conditional with Polymorphism sketch replaces a `switch` on a type field. “or a lookup table”, “move to shared module” and “/ builder” are not catalog refactorings (lesson’s own additions; the “replace conditional with lookup” step is not presented as a named refactoring). |
| Refactoring catalog: Replace Primitive with Object (aliases Replace Data Value with Object, Replace Type Code with Class) | “Primitive obsession → Introduce value object (`Money`)” (`refactoring-lesson`) | **Fixed wording:** no catalog refactoring is called “Introduce value object”; → “Replace primitive with object (a `Money` value object)”. |
| Refactoring catalog (no smells section); bliki CodeSmell | Smell names (Long function, Duplicated code, repeated switch, Long parameter list, Feature envy, Primitive obsession) and which refactoring fixes each | Not covered: the smells chapter is not in the online catalog. The CodeSmell bliki (author’s article, not a book summary) confirms only the idea (a smell is a quick-to-spot surface sign that usually, not always, indicates a deeper problem; long methods as the example). Pairings unchecked. |
| bliki TestDouble (Fowler, citing Meszaros) | Fake = working lightweight version (in-memory); stub = canned answers; “a **mock** records calls so you can assert on them” (`testing`) | Fake and stub match. **Fixed wording:** in this vocabulary a double that records calls is a *spy*; a mock is pre-programmed with expected calls. → “A **spy** records calls so you can assert on them (…); Python calls these mocks (`unittest.mock`) … use spies when the interaction itself is the behaviour”; table row “Mock / spy” → “Spy (Python: mock)”. This page is not the Refactoring book; proposed as a separate source entry (below). |
| PoEAA catalog: Repository | Repository gives domain code a collection-like interface (`get`, `save`) and hides SQL and row ↔ object mapping; in-memory version for tests (`domain-objects`) | Matches (“mediates between the domain and data mapping layers using a collection-like interface”; objects added/removed as from a collection; mapping code encapsulated). “Caching” and “HTTP” behind a repository are not stated: lesson extension. |
| PoEAA catalog: Unit of Work, Identity Map, Optimistic Offline Lock | (none) | Read; no lesson citing `poeaa` makes a claim about these patterns. |
| DDD Reference: Value Objects | Value object has no identity, compared by value, immutable (`domain-objects`) | Matches (“no conceptual identity … care only about the attributes … treat the value object as immutable … side-effect-free functions”). Example list (seat numbers, dates, addresses, money) not in the summary. |
| DDD Reference: Entities | Entity keeps its identity while attributes change; has a lifecycle; compare by id, not fields (`domain-objects`) | Matches (“thread of continuity and identity, going through a lifecycle, though their attributes may change”; distinguished even with the same attributes). **Fixed code:** `python/sdm/lld.py` `Booking` was a plain `@dataclass`, whose generated `__eq__` compares all fields, contradicting “Equal if ids equal”; now `@dataclass(eq=False)` with `__eq__`/`__hash__` on `booking_id`, plus `test_entity_equality_is_by_id` in `python/tests/test_lld.py`. |
| DDD Reference: Aggregates | “An aggregate groups entities that must change together under one root … outside code goes through the Order” (`domain-objects`) | Matches with a qualifier. **Fixed wording:** the reference clusters “the entities **and value objects**” → “groups entities and value objects that must change together”. Root-only external references, root enforces invariants, boundaries govern transactions: confirmed. |
| DDD Reference: Repositories | Repository = collection-like access, hides storage (`domain-objects`) | Matches (“illusion of an in-memory collection of all objects of that aggregate’s root type … encapsulating the actual storage and query technology”). The reference says repositories are for aggregate roots that need global access; the lesson does not contradict this. |
| DDD Reference: Bounded Context, Aggregates | Draw service boundaries around data that changes together and is owned by one team; two services sharing a table in one transaction are one service split badly (`monolith-microservices`) | Partly covered: boundaries are set “in terms of team organization … code bases and database schemas” (Bounded Context); consistency rules apply synchronously within an aggregate boundary and asynchronously across (Aggregates). The reference (2004 material) says nothing about microservices, deploys or a team of six: those claims are not from this source. |
